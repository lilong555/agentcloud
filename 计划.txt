# AgentCloud：上游源码审计、架构裁决与分阶段实施计划

**检查日期：2026-11-09，Asia/Singapore。**

**文档状态：调研与规划完成；功能实现、部署和性能实验均未执行。**

## 1. 项目摘要与核心定位

### 1.1 一句话定义

**[合理推断] AgentCloud 是建立在 Substrate 与 Dynamo 之上的跨层等待协调与恢复验证平台，研究何时将推理等待移出执行沙箱、何时释放执行容量，以及 Workspace 生命周期信号是否能改善推理调度。**

项目的核心成果应当是：

- 明确、可检验的请求与恢复协议。
- 优于简单闲置策略的增量收益，或者说明其没有收益的负结果。
- 能复现的资源归因、消融实验和故障注入。
- 少量有明确边界的上游适配或改进。

### 1.2 必须修改初始方案的五个前提

| 初始设想 | 审计后的裁决 |
|---|---|
| Actor 同步等待 HTTP，因此无法 Suspend | **[已验证事实]** Substrate 可以挂起，但会取消或关闭相关网络连接。问题是等待所有权和断连后的执行歧义。 |
| 对象存储提供跨代增量快照 | **[已验证事实]** 本次源码不能支持这一宣传。microVM 会将按需恢复产生的稀疏差量合并为自包含快照。 |
| 直接以 Python `thunderagent_router` 的参数设计新系统 | **[已验证事实]** 当前主线已有原生 Rust ThunderAgent 插件；Python 原型与原生实现的参数、容量模型和状态接口不同。 |
| `trajectory_final`、`evict_trajectory` 可用于 Workspace 休眠反馈 | **[已验证事实]** 当前源码未实现这些假定接口；`nvext.agent_context` 甚至有明确的拒绝测试。 |
| Workspace、Session、快照恢复控制面本身是主要创新 | **[已验证事实]** AX、kagent 已覆盖大量相关能力；kagent 还已有闲置挂起、checkpoint/fork 和未知生命周期结果处理。 |

证据见 Substrate 的 [挂起实现说明][S4]、[快照合并代码][S5]，Dynamo 的 [请求扩展定义及测试][D3]，以及 [AX 架构][A1]、[kagent 架构][K1]。

### 1.3 Goals 与 Non-Goals

| 范围 | 裁决 |
|---|---|
| Goals | **[合理推断]** 持久工作目录、受控 Shell/文件工具、单写者生命周期协调、等待期间释放可复用容量、请求与恢复结果对账、端到端追踪、消融与故障注入。 |
| 核心研究问题 | **[待验证假设]** 在执行容量有竞争、推理等待足够长且快照成本可承受时，协调策略能否优于最佳简单闲置策略，同时保持交互 SLO 和正确性？ |
| Non-Goals | **[合理推断]** 商业 SaaS、计费、多组织权限、复杂前端、Agent 模板市场、自研容器运行时、重写 KV router、全局多集群调度、首版自动高可用控制面。 |
| 多租户范围 | **[合理推断]** 首版验证多个逻辑租户的身份隔离、配额和受控工具权限；不宣称已经完成生产级多租户安全认证。 |
| 浏览器 | **[合理推断]** 后续能力项。首版只验证 Shell/文件；浏览器进程可快照，不代表远端登录态、WebSocket 和外部服务会话能续接。 |

### 1.4 技术栈裁剪

**[合理推断] 推荐采用：**

- **Go**：协调器、网关、请求 Journal、执行对账、实验控制。
- **Python**：Synthetic Runtime 与 DeerFlow 适配。
- **Substrate**：Actor、隔离、快照、Worker 调度、按需唤醒。
- **Dynamo 原生 ThunderAgent**：程序级准入和 KV-aware routing。
- **PostgreSQL**：意图、回执、映射、manifest。
- **OpenTelemetry**：跨层观测。
- **Kubernetes**：运行上游组件和配置 WorkerPool。

**[合理推断] Rust 仅在 P0 证明扩展必要、接口边界清楚后引入。** 首版不额外增加 Redis、Kafka、自研 Operator，也不为每个 Workspace 创建 CRD。

### 2.2 Substrate 审计

#### 资源所有权

| 对象 | 管理者 | 结论 |
|---|---|---|
| `WorkerPool` | Kubernetes CRD | **[已验证事实]** 管理 Worker 的期望配置。 |
| `SandboxConfig` | Kubernetes CRD | **[已验证事实]** 管理沙箱运行时配置。 |
| `Actor` | ateapi / PostgreSQL | **[已验证事实]** 不是每 Actor 一个 K8s CRD。 |
| `ActorTemplate` | ateapi / PostgreSQL | **[已验证事实]** 保存业务镜像及运行配置。 |
| `Atespace`、`Tag` | ateapi / PostgreSQL | **[已验证事实]** 属于 Substrate 控制 API。 |
| Worker records、assignments、leases | ateapi / PostgreSQL | **[已验证事实]** 承担运行态容量和生命周期协调。 |

证据：[Control protobuf][S1]、[Substrate 架构][S2]。

**[已验证事实]** `ate-controller` 将 WorkerPool 协调为 Worker Deployment 等对象，workersync 将 Pod 状态同步成 ateapi Worker records。Actor 激活时由 ateapi 选择 Worker，不为每次激活重新走一遍 K8s Pod 调度。

#### 核心调用链

**[已验证事实] 恢复路径：**

`atenet-router → Control.ResumeActor → ateapi 调度与 assignment → atelet.Restore/Run → Worker.RestoreWorkload/RunWorkload → wakeupProbe → 请求进入 Actor`

**[已验证事实] 挂起路径：**

`Control.SuspendActor → Actor lease / SUSPENDING → atelet.Checkpoint → Worker.CheckpointWorkload → tunnel.Deactivate → snapshot / teardown → 释放 assignment → SUSPENDED`

| 组件 | 实际职责 |
|---|---|
| `ate-api-server` | **[已验证事实]** 公开 Control API、内部 WorkerService、PG 状态、租约、调度与 golden snapshot 工作流。 |
| `atenet-router` | **[已验证事实]** Envoy `ext_proc`，识别目标 Actor、请求恢复、Parking、建立到 Worker 的 tunnel。 |
| `atelet` | **[已验证事实]** 节点本地运行时资产准备、快照上传下载、调用 Worker、后台持久化与报告。 |
| Worker | **[已验证事实]** 执行 gVisor 或 Cloud Hypervisor 沙箱，管理进程、内存、文件系统和 tunnel。 |

#### 真实接口

**[已验证事实] 公开接口包括：**

```text
Control.GetActor(GetActorRequest) -> Actor
Control.CreateActor(CreateActorRequest) -> Actor
Control.SuspendActor(SuspendActorRequest) -> SuspendActorResponse
Control.ResumeActor(ResumeActorRequest) -> ResumeActorResponse
Control.ListWorkers(ListWorkersRequest) -> ListWorkersResponse
Control.ListWorkerActorAssignments(...) -> ...
```

**[已验证事实] 关键请求形状：**

```text
SuspendActorRequest {
  actor: ObjectRef
  options: SuspendOptions { mode: DurabilityMode }
}

ResumeActorRequest {
  actor: ObjectRef
}
```

这两个公开请求**没有 AgentCloud epoch、expected version 或操作幂等键**。[S1]

**[合理推断]** “先读取 UID，再调用 Suspend”仍然存在 TOCTOU；外围数据库 epoch 不会自动变成上游 RPC 的 fencing 条件。

#### 快照语义

| 项目 | 结论 |
|---|---|
| VOLUMES | **[已验证事实]** 保存 DurableDir。 |
| ROOTFS | **[已验证事实]** 再包含容器可写文件系统。 |
| MEMORY | **[已验证事实]** 再包含进程和内存状态。 |
| gVisor | **[已验证事实]** 使用 `runsc checkpoint`，指定 image/fs-checkpoint 路径。 |
| Cloud Hypervisor | **[已验证事实]** pause/snapshot VM，保存状态和内存，宿主另保存可写层及卷。 |
| 对象存储增量 | **[已验证事实]** 当前 microVM 会把 OnDemand delta 合并成自包含快照；不能称为跨代只上传增量。 |
| 默认 durability | **[已验证事实]** Suspend 默认 ASYNCHRONOUS；SUSPENDED 时对象存储可以仍为 PENDING。 |
| 已经 SUSPENDED 后再调 sync | **[已验证事实]** 直接返回原状态，不是强制升级为 durable 的 API。 |
| MEMORY 恢复 | **[已验证事实]** 有 runtime/hardware 兼容要求；可能降为 ROOTFS 冷启动。 |

证据：[挂起工作流][S3]、[microVM 快照合并][S5]、[API 指南][S7]。

**[已验证事实]** `snapshot.fidelity` 描述的是保存的快照，不必然是这次实际恢复方式；Resume 工作流会单独计算降级后的 fidelity。[S12]

**[待验证假设]** Mode A 应通过受控 Runtime 的 RAM nonce、boot generation 和上游 wire-fidelity 遥测交叉确认恢复方式，不能只看 Actor RUNNING。

#### 多模板、Parking、预热与观测

**[已验证事实]**

- 不同业务镜像可以共享兼容的 WorkerPool。
- 约束包括 sandbox class、selector、runtime/hardware、资源、镜像可达性和快照兼容性。
- 一个 Worker 可以承载多个 Actor；容量包括 slots、CPU、RAM 和运行时开销。
- 已有按需 Resume、singleflight、Request Parking、golden snapshot、runtime asset prewarm、本地快照缓存。
- `--parked-request-budget` 默认 5 秒、`--parked-request-max` 默认 1024；这是配置默认值，不是实测性能。
- Parking 等待的是执行层 placement，不能当成 GPU admission queue，也不是持久请求队列。
- Worker capacity/allocated、Actor usage、parking 指标、Actor 生命周期事件可用于观测。
- 未发现公开 WatchActors RPC；事件可能丢失，一致性必须通过 Control API 对账。

证据：[调度器][S8]、[Parking][S9]、[可观测性指南][S10]。

#### 网络与在途工具

**[已验证事实]** Checkpoint 前会 Deactivate tunnel，取消 ingress 并关闭 egress。活跃 HTTP、SSE、TCP 没有跨 Suspend 透明续传保证。上游源码还明确提醒：挂起取消在途请求，而不是等待所有请求自然 drain。[S4]

**[合理推断]** 因此需要解决的是：

1. 谁继续持有模型请求。
2. 谁保存已经到达的结果。
3. 恢复后如何认领同一个逻辑请求。
4. 断线时如何区分未执行、已执行和结果未知。

### 2.3 Dynamo / ThunderAgent 审计

**[已验证事实]** 当前新部署路径是原生 Rust ThunderAgent builtin plugin，运行在 frontend 内；旧 Python `dynamo.thunderagent_router` 被文档称为 older prototype。两者均需按实验性能力对待，不能混用参数和保证。[GitHub](https://github.com/ai-dynamo/dynamo/blob/main/docs/fern/pages/use-cases/agents/thunderagent-program-scheduler.md?utm_source=chatgpt.com)

| 核查项 | 结论 |
|---|---|
| 原生路径 | **[已验证事实]** `lib/router-plugins/builtin/src/thunderagent/`。 |
| Python 原型 | **[已验证事实]** `components/src/dynamo/thunderagent_router/`。 |
| 插件角色 | **[已验证事实]** 同时注册 request classifier 和 worker selector。 |
| 原生部署方式 | **[已验证事实]** 使用 router-policy YAML，选择 `thunderagent`。 |
| 状态机 | **[已验证事实]** `Reasoning/Acting` × `Active/Paused`，另有 `marked_for_pause` 和请求 Waiting/Released。 |
| 公共身份协议 | **[已验证事实]** `X-Dynamo-Session-ID`、`X-Dynamo-Parent-Session-ID`、`X-Dynamo-Session-Final`。 |
| `nvext.agent_context` | **[已验证事实]** 外部请求字段被拒绝，源码有对应测试。 |
| 无 Session ID 的请求 | **[已验证事实]** 绕过 program admission；不能用这种流量验证暂停。 |

| 多 frontend | **[已验证事实]** program state 在单 frontend 内，不是集群全局预算。 |

证据：[原生指南][D1]、[scheduler][D2]、[扩展定义与拒绝测试][D3]。

#### 暂停、衰减与恢复

**[已验证事实]**

- 超阈值后先暂停 Acting program。
- 若不够，再标记正在 Reasoning 的 program，等本次生成完成后暂停。
- 不在生成中途抢占 GPU request。
- `pause_acting` 只改变生命周期并清除 assignment。
- 正常逻辑用量为 token 数乘以 `acting_token_weight`，再加 buffer。
- 原生容量来自 GPU blocks × block size，不包含 Python 原型的 host-cache budget，也不去重共享 prefix。

**[已验证事实] 原生参数是 YAML 字段：**

```text
pause_threshold
pause_target
resume_hysteresis
resume_timeout_seconds
acting_token_weight
acting_decay_tau_seconds
session_retention_seconds
```

`--pause-threshold` 之类连字符 CLI 属于 Python 原型。

**[已验证事实] 衰减公式为：**

\[
T_{\mathrm{decayed}}
=
\left\lfloor T \cdot 2^{-idle/\tau}\right\rfloor
\]

其中 \(\tau\) 是半衰期。该衰减用于 timeout fallback placement，**不是物理 KV retention weight，也不是所有正常准入都使用衰减**。[D2]

**[已验证事实]** `resume_timeout_seconds` 到期后尝试向 live worker 强制释放请求，不是直接返回超时拒绝，也不保证端到端 SLO。

#### Pre-admission 的真实边界

**[已验证事实] 内部接口是：**

```text
RequestClassifier::classify(
    &mut self,
    request: ClassifyRequest,
    workers: WorkerCandidates<'_>
) -> ClassifyFuture
```

内部事件包括 Sent、Responding、Completed、Aborted。

**[已验证事实]** 未发现公开的原子 probe/reserve/commit API 或持久异步准入通知。Future 可以等待，但 HTTP 连接仍然需要调用者维持。[D5]

**[合理推断]** MVP 应让外部 Broker 持有这个等待；不能假设通过一次“查询是否 PAUSED”就获得未来 GPU 容量的保证。

#### 取消与 Final

**[已验证事实]** pending classification 被取消时，Drop guard 会清理新 program 或恢复原有 program 的 prior state。这是进程内准入回滚，**不代表 GPU 计算或计费被撤销**。[D4]

**[已验证事实]**

- 原生 Final 清理 program accounting。
- Python 原型对 Final 有 short-circuit，不调用 engine。
- 原生 classifier 释放请求后仍进入后续 pipeline。

**[待验证假设]** 原生 dedicated Final 是否造成 backend 调用，必须在 P0 实测；不能直接继承 Python 原型的“无 token 成本”语义。

**[合理推断] Workspace Suspend 不发送 Final。** 休眠的 Workspace 仍可能继续原 trajectory；Final 既会清掉调度历史，也不能保证物理 KV 被释放。

#### KV-aware routing、卸载与 hints

**[已验证事实]** 当前 `KvHint` 是版本化的内部提示，包含 `kv.fetch@1.0`、block hashes 等信息；hint 不是 pin，也不是 `evict_trajectory`。[D6]

**[已验证事实]** 当前可复用的公开请求提示包括：

```text
nvext.agent_hints.priority
nvext.agent_hints.strict_priority
nvext.agent_hints.osl
nvext.agent_hints.speculative_prefill
```

**[已验证事实]** Dynamo 官方能力说明列出 SGLang 的请求优先级相关缓存策略，而 vLLM 的 cache eviction priority 仍标为 Planned。请求 priority 不能等同于静默期修改已缓存 Session 的权重。[D7]

**[已验证事实]** ThunderAgent 不直接替 HiCache 发起 eviction、restore、prefetch 或 Mooncake 控制。

**[合理推断]** B 应拆为：

1. 上游已有的逻辑准入账本。
2. 请求时可复用的 priority/hints。
3. 尚需 backend 原语的物理 eviction/offload。

三者不能合并成一个“KV 生命周期控制”指标。

#### 无卡测试

**[已验证事实]** 上游已有 `dynamo.mocker`，支持真实 worker 注册、KV events、容量/负载指标，以及 file discovery。本项目不需要再实现一套 ZMQ/gRPC Mock Engine。[D9]

**[合理推断]** 无卡可以跑真实 Router，但不能证明真实 GPU 性能。编译、运行环境和 tokenizer/config 仍需准备。

### 2.4 DeerFlow 审计

**[已验证事实]** 本次主线已经将 App Gateway 与 Harness 分开：

- Gateway：run/API/stream。
- Harness：Agent loop。
- SandboxProvider：工具执行环境。
- Checkpointer：graph state。

它们不共享同一种状态恢复保证。[F1]

| 接缝 | 核验结果 |
|---|---|
| Provider 加载 | **[已验证事实]** `config.sandbox.use` 动态加载外部 Provider。 |
| Provider 方法 | **[已验证事实]** `acquire`、`acquire_async`、`get`、`get_scoped`、`release`。 |
| `get_scoped` | **[已验证事实]** 必须是非阻塞内存查找，不能在里面调用 Substrate RPC。 |
| Sandbox 方法 | **[已验证事实]** 命令、文件读写、上传下载、glob/grep 等；没有现成 suspend/resume 抽象。 |
| 模型接缝 | **[已验证事实]** MODEL_LOGICAL 与 MODEL_PHYSICAL，分别对应逻辑调用和物理 attempt。 |
| 工具接缝 | **[已验证事实]** TOOL_RAW、TOOL_VISIBLE，支持 lead/subagent scope。 |
| Checkpointer | **[已验证事实]** 支持 AsyncPostgresSaver；但子 agent 显式 `checkpointer=False`。 |
| 执行 lease | **[已验证事实]** 已有进程内 holder、取消后 drain；不等于跨进程独占执行。 |
| RunJournal | **[已验证事实]** 不记录逐 token 回调。 |
| StreamBridge | **[已验证事实]** 支持客户端重放，但存在 TTL、trim 和 StreamGap。 |

证据：[Provider][F2]、[Sandbox][F3]、[扩展 placement][F4]、[子 agent 创建][F6]、[RunJournal][F7]。

**[已验证事实] Extension 真实签名：**

```text
contribute_middlewares(
    self,
    app_store: ExtensionData,
    ctx: AgentBuildContext
) -> Sequence[MiddlewarePlacement]
```

**[合理推断]** 可非侵入实现 `SubstrateSandboxProvider + Sandbox + extension`，但 before_model 不能证明整个 Workspace 静止。

安全点至少要覆盖：

- 并行子 agent。
- 已受理工具。
- 文件上传。
- 后台 Shell。
- 超时但仍运行的命令。
- 外部 Harness 对模型结果的应用。

**[合理推断] Mode B 已消除了 A 的部分结构性问题。** LLM HTTP 在外部 Harness 中，Actor 只执行工具。研究增量应是“GPU/执行压力感知的休眠时机是否优于 eager/TTL”，不能把外置 Harness 本身包装成新的调度机制。

## 3. 核心假设批判性验证与系统权衡

### 3.1 假设 A：保留等待外移，否决未证实的原子预准入

**[合理推断] 裁决：条件成立，但必须改写前提。**

MVP 应实现：

> 外部持有推理请求，Actor 在全局安全点释放执行容量。

不能宣称：

> 已利用 Dynamo 原子预准入接口，保证 Actor 一定在 GPU admission 前挂起。

因为当前没有这样的公开接口。

#### 两种最小实现

| 路线 | 行为 | 保证与代价 |
|---|---|---|
| Broker 代持 | Journal durable 后立即提交 Dynamo，Controller 再根据等待成本决定是否挂起 Actor。 | **[合理推断]** 无需新上游 API；但挂起前推理可能已经开始。 |
| Gateway 先排队 | 请求先留在 AgentCloud 队列，安全挂起 Actor 后再提交 Dynamo。 | **[合理推断]** 可以保证提交顺序，但本地准入是代理策略，Dynamo 可能再次排队。 |

**[合理推断] 正确顺序：**

1. Runtime 登记稳定逻辑请求并获得 durable receipt。
2. Coordinator 原子关闭 Workspace 的新操作准入。
3. Runtime drain 已受理操作，返回匹配 barrier 的 ACK。
4. 外部 Coordinator 发起 Suspend。
5. Broker 保存模型结果。
6. 外部恢复 Actor。
7. Runtime 按原 request ID 认领结果。

**[合理推断]** Runtime 不应在自己的 HTTP handler 内等待“自身 Suspend 完成”；外部控制器负责完成对账。

#### 收益模型

设：

- \(H\)：真正释放执行容量的时长。
- \(m\)：可回收内存 GB。
- \(c\)：可回收 reserved CPU cores。
- \(p_m,p_c\)：资源时间的价值。
- \(\Delta L\)：端到端延迟增量。

**[合理推断]：**

\[
\Delta V_A
=
(p_m m+p_c c)\mathbb E[H]
+
V_{\mathrm{queue\ relief}}
-
C_{\mathrm{snapshot}}
-
C_{\mathrm{restore}}
-
C_{\mathrm{journal}}
-
C_{\mathrm{recompute}}
-
\lambda\mathbb E[\Delta L].
\]

**[合理推断]** 只有保守估计 \(\Delta V_A>0\)、交互延迟预算允许且执行容量存在竞争时才休眠。

还需要：

- 最小驻留/休眠时间。
- 冷却窗口。
- 单 Workspace 切换频率上限。
- 指标过期后的回退。
- 恢复并发限制。

**[合理推断] 反例：**

- Mode B 本来已经把模型连接放在外部。
- 模型排队很短。
- Actor 很小。
- MEMORY 快照很大。
- 执行层完全不缺容量。
- 释放 Actor 后节点仍不能缩容或接纳其他工作。

这些情况下，复杂协调可能没有收益。

### 3.2 假设 B：否决“一休眠就 Evict”

**[合理推断] 裁决：物理 KV 控制不进入默认 MVP。**

| 动作 | 适用条件 | 当前处理 |
|---|---|---|
| Direct eviction | 长期不复用、真实容量压力、共享引用安全。 | **[待验证假设]** 需要 backend 原语和执行回执。 |
| L2/L3 offload | 复用概率较高，GPU 紧张，下层容量和传输预算充足。 | **[合理推断]** 先复用后端机制，不由 AgentCloud 猜测内部状态。 |
| 降低逻辑权重 | 生命周期信号比静态估计更准，且不会引入过量准入。 | **[待验证假设]** 可研究，但指标只能称逻辑预算。 |
| 请求 priority/hints | 有真实下一请求且 backend 支持。 | **[已验证事实]** 有现成接缝；静默时不能靠 header 传递事件。 |

#### 成本模型

设：

- \(B\)：正确去重或分摊后的 KV GB。
- \(H\)：保留窗口。
- \(q\)：窗口内回访概率。
- \(r\)：回访时下层缓存仍可用的概率。

**[合理推断]：**

\[
C_{keep}=p_gBH
\]

\[
C_{evict}
=
q(C_{prefill}+\lambda L_{prefill})
\]

\[
C_{offload}
=
p_hBH+C_{D2H}
+
q\left[
r(C_{H2D}+\lambda L_{H2D})
+
(1-r)(C_{prefill}+\lambda L_{prefill})
\right].
\]

**[合理推断]** 应比较增量机会成本，而非直接看到缓存占满就驱逐：

- 无 GPU 压力时，保留机会成本可能很低。
- 可回收 prefix cache 不等于被独占的显存。
- 共享块不能重复计算。
- host/storage 命中率不能假定为 100%。
- 淘汰后的 re-prefill 可能抵消收益。

**[合理推断]** 不能预先承诺“几十行 Rust”。一个可信的新 lifecycle 协议至少涉及身份、epoch、序号、失联、重放、过期、并发、观测和测试；物理缓存控制还涉及 backend 引用关系。

### 3.3 假设 C：保留一致性协议，限制恢复承诺

**[合理推断] 裁决：Mode B 为真实框架主线；Mode A 为受控实验。**

- Mode A 的内存快照不包含外部世界，且存在 fidelity 降级。
- Mode B 的 graph checkpoint 与 Actor snapshot 不共享事务。
- 两阶段“准备—发布”是状态对账协议，不是跨 PostgreSQL 与对象存储的强事务。
- 外部写操作的 UNKNOWN 不能因为回滚快照而消失。

### 3.4 假设 D：真实收益象限

| 资源状态 | 预期 | 可证伪点 |
|---|---|---|
| CPU/RAM 紧、GPU 闲 | **[合理推断]** 普通 idle-suspend 可能有效。 | **[待验证假设]** 跨层策略不应明显优于调优后的 idle 基线。 |
| GPU 紧、执行层闲 | **[合理推断]** 可减少驻留，但通常不提升 GPU 吞吐。 | **[待验证假设]** 快照和 re-prefill 可能抬高 TTFT、降低 Goodput。 |
| 双拥塞 | **[合理推断]** 最值得验证。 | **[待验证假设]** 快照 I/O、CPU 和恢复风暴可能成为新瓶颈。 |
| 低负载 | **[合理推断]** 默认直通并保留缓存。 | **[待验证假设]** 主动休眠通常只有额外开销。 |

**[待验证假设] 预注册命题：**

- H-A：双拥塞长等待区，D 相对 C 减少受阻驻留，并提高交互 Goodput。
- H-0：低负载和短等待区不超过预设回归容忍度。
- H-B：存在真实 KV 执行器时，E 相对 D 改善 Goodput，且不显著增加 re-prefill。
- H-C：规定故障模型内，不发布错配 manifest，不自动重放 UNKNOWN 副作用。

## 4. 整体架构与数据面/控制面设计

### 4.1 最小架构

**[合理推断]** 首版 Coordinator、Gateway、Dispatcher 合在一个 Go 进程中，保持逻辑分层即可。

```mermaid
flowchart TD
    Client["CLI / API 客户端"] --> Gateway["Gateway + Journal（自研）"]
    Gateway --> DB[("PostgreSQL：意图 / 回执 / Manifest")]
    Gateway --> Runtime["Synthetic 或 DeerFlow Harness"]
    Runtime --> Tools["Tool Gateway：准入与 Epoch（自研）"]
    Tools --> Actor["Substrate Actor：Shell / 文件"]
    Runtime --> Broker["模型等待 Broker（自研）"]
    Broker --> Dynamo["Dynamo + ThunderAgent（复用）"]
    Dynamo --> Engine["Mocker / 真实 Engine（复用）"]
    Coordinator["Coordinator：策略与对账（自研）"] --> DB
    Coordinator --> Substrate["ateapi / atelet / Worker（复用）"]
    Substrate --> Actor
    Substrate --> Snapshot[("上游快照存储")]
    Coordinator -. "策略信号" .-> Broker
```

**[合理推断]**

- 数据面处理模型、工具和结果。
- 控制面处理期望状态、快照、epoch 和对账。
- OTLP/指标只提供观测，不作为事务提交确认。
- 不直接写 Substrate 或 LangGraph 的内部表。
- 用户输入的标识必须绑定认证租户，不能允许伪造其他租户的 Dynamo Session。

### 4.2 四元组身份映射

| 对象 | 生命周期 | 身份规则 |
|---|---|---|
| Workspace | **[合理推断]** 持久文件和环境，可跨多个 Session。 | `tenant_id + workspace_id`；首版单写入执行者。 |
| Session | **[合理推断]** 一段对话/工作上下文。 | `session_id`，映射 DeerFlow `user_id/thread_id`。 |
| Actor | **[已验证事实]** 可被替换的执行实体。 | 保存 atespace/name/UID；额外绑定 template UID 和 epoch。 |
| Trajectory | **[合理推断]** 一条串行推理—工具链。 | 映射 opaque Dynamo session ID；子 agent/fork 使用新 ID。 |

**[合理推断]** 额外区分：

- `logical_request_id`
- `attempt_id`
- `tool_operation_id`
- `checkpoint_id`
- `snapshot_generation`
- `workspace_generation`

同一 Trajectory 恢复继续原 Session ID；真正 fork 使用新 ID。Workspace Suspend 不发送 Final。

### 4.3 联合状态机

**[合理推断]** 执行层与模型层独立保存状态。恢复 Actor 不代表模型结果已经完成。

```mermaid
stateDiagram-v2
    state "Actor RUNNING / 模型状态独立" as Running
    state "Actor RUNNING / 请求已登记" as Registered
    state "QUIESCING / 新工具已关闭" as Quiescing
    state "Actor SUSPENDED / Broker 排队" as Parked
    state "Actor SUSPENDED / Broker 生成" as Inferring
    state "RESUMING / 模型状态独立" as Resuming
    state "RECOVERY_REQUIRED / 结果未知" as Unknown
    state "终态 / 调度会话结束" as Finished

    [*] --> Running
    Running --> Registered: 持久提交逻辑请求
    Registered --> Running: 短等待或无收益，直通
    Registered --> Quiescing: 全局安全点与收益门槛
    Quiescing --> Parked: 挂起与快照对账完成
    Parked --> Inferring: Broker 获得推理执行
    Inferring --> Resuming: 持久结果或唤醒条件
    Parked --> Resuming: 用户返回或需要工具
    Resuming --> Running: Epoch 与恢复水位通过
    Quiescing --> Unknown: RPC 结果不明
    Inferring --> Unknown: 后端执行结果不明
    Resuming --> Unknown: 快照或回执不匹配
    Unknown --> Resuming: 有证据完成对账
    Running --> Finished: 任务确实终止
```

**[合理推断]** Broker 代持路线可能在 QUIESCING 时已经推理；图中“先挂起再生成”只对应 Gateway 先排队路线。用户返回时 Broker 可能仍排队，不能把恢复事件解释为模型完成。

## 5. 关键跨层协议与一致性设计

### 5.1 Runtime Contract

**[合理推断] 以下均为拟定的 AgentCloud 接口，不是上游现有 API。**

| 接口草案 | 语义 |
|---|---|
| `GET /runtime/v1/capabilities` | 声明 snapshot fidelity、后台任务策略、取消能力、模型调用所在位置和流重放能力。 |
| `GET /healthz` / `GET /readyz` | 区分存活、沙箱启动就绪与业务写准入。 |
| `POST /runtime/v1/quiesce` | 输入 operation ID、当前 epoch、barrier generation；drain 已受理操作并返回匹配水位。 |
| `POST /runtime/v1/attach` | 校验新 epoch、manifest、Actor UID、boot generation、恢复证明。 |
| `POST /v1/model-requests` | 持久接收稳定 logical request ID、payload hash、trajectory、deadline。 |
| `GET /v1/model-requests/{id}` | 查询状态/结果，不隐式重新派发。 |
| `GET /v1/model-requests/{id}/events?after_seq=N` | 重放已持久 chunk，明确报告 gap/incomplete。 |
| `POST /v1/tools/{operation_id}` | 绑定 tenant、Workspace、epoch、payload hash；拒绝同 ID 不同 payload。 |

**[合理推断] readiness 必须避免死锁。** Substrate Resume 会等待 wakeupProbe，因此该 probe 在“服务已启动，但写 gate 仍关闭”时即可返回 200。若 readyz 等 attach，而 Coordinator 等 Resume 返回后才 attach，会相互等待。

**[待验证假设]** 本次实际恢复 fidelity 的观测接缝要在 P0 验证；不能读取 snapshot.fidelity 就认为已经证明内存连续恢复。

### 5.2 Mode A 与 Mode B

```mermaid
flowchart TD
    subgraph A["Mode A：Synthetic 验证"]
        AH["Actor 内 Harness + 工具"] --> AJ["Actor 外 Journal / Broker"]
        AJ --> AM["模型服务"]
        AC["外部 Coordinator"] --> AH
    end

    subgraph B["Mode B：DeerFlow 主线"]
        BH["外部 Harness + Checkpointer"] --> BJ["模型网关"]
        BH --> BG["Tool Gateway"]
        BG --> BA["Actor 仅运行工具"]
        BC["外部 Coordinator"] --> BA
    end
```

**[合理推断]**

- Mode A 首先只支持受控 Runtime 主动交出等待，不承诺任意 Harness 的透明改造。
- Mode B 的外部 Harness 可以保持 async await，工具 Actor 独立休眠。
- “暂时休眠工具 Actor”与“外部 Harness 崩溃后可恢复的联合 manifest”是两个保证等级。

### 5.3 正常等待外移

**[合理推断]** 以下采用 Gateway 先排队路线。

```mermaid
sequenceDiagram
    participant R as Runtime
    participant J as Journal / Broker
    participant C as Coordinator
    participant S as Substrate
    participant D as Dynamo / Engine

    R->>J: 提交 logical_request_id 与 payload_hash
    J->>J: PG 提交意图和待派发记录
    J-->>R: durable receipt
    R->>C: 请求进入安全点
    C->>C: CAS 为 QUIESCING，原子关闭全局新准入
    C->>R: quiesce(operation_id, barrier_generation)
    R->>R: drain 已受理操作并持久保存回执
    R-->>C: 匹配 barrier 的 ACK 与无洞水位
    C->>C: 复核 gate 未重开且在途为零
    C->>S: SuspendActor
    S-->>C: 状态和 snapshot generation
    C->>S: 查询同 UID / generation 的 durable 状态
    S-->>C: COMPLETED
    C->>J: 允许派发
    J->>D: 一个物理 attempt
    D-->>J: 结果或 token stream
    J->>J: 持久保存结果 / 有序 chunk
    J-->>C: 结果可用
    C->>S: ResumeActor
    S-->>C: RUNNING
    C-->>R: attach 新 epoch 与 manifest
    R->>J: 按 request_id 和 cursor 认领
    J-->>R: 重放已提交结果
```

**[合理推断] 关键并发规则：**

1. gate 检查与操作登记必须原子完成。
2. 不能“先读 open，稍后再启动工具”。
3. Quiesce 使用独立 `barrier_generation`。
4. 已受理操作继续使用原 execution epoch 提交终态回执。
5. 恢复 attach 时才切换 epoch。
6. gate 关闭期间新操作返回明确可重试状态，不进入 Actor ingress 意外唤醒。

**[合理推断]** P2 第一版只做非流式完整结果，随后增加有界 chunk spool。限制请求数、请求体、结果体、chunk retention 和总缓冲字节；满额后停止接收新任务。

### 5.4 故障恢复与 exactly-once 边界

```mermaid
sequenceDiagram
    participant R as Runtime
    participant J as Journal
    participant W as Dispatcher
    participant D as Engine

    W->>J: CAS 认领，记录 DISPATCHING 与 attempt_id
    W->>D: 发出模型请求
    D-->>W: 可能已接受 / 执行
    Note over W: 进程崩溃或响应丢失
    R->>J: 重复提交同一 logical_request_id
    J-->>R: 返回原记录
    W->>J: 重启扫描未完成派发

    alt 后端有经验证的去重和结果查询
        W->>D: 查询原 attempt
        D-->>W: 可核验执行结果
        W->>J: 提交唯一结果
    else 无可核验执行状态
        W->>J: 标记 OUTCOME_UNKNOWN
        J-->>R: 请求对账，不自动重发
    end
```

**[合理推断] Journal 提供的保证：**

| 层次 | 可以保证 | 不能据此保证 |
|---|---|---|
| 入口 | 相同 logical ID、相同 payload 返回同一记录。 | 后端只计算一次。 |
| 结果提交 | 一个有效 owner 提交最终结果。 | 旧 owner 没有已经向后端发出请求。 |
| Stream | 已持久 chunk 可重放。 | 任意断开的 GPU 生成可继续。 |
| 恢复 | 已接收意图仍可查询。 | 无后端查询时自动辨明是否已经扣费。 |

**[合理推断]** DISPATCHING 后结果不明，不能只因 lease 到期就重发。需要 backend 的执行幂等与查询原语，否则进入 UNKNOWN。

**[合理推断]** 还要审计 SDK/Harness 自动重试。一个 MODEL_PHYSICAL 回调可能仍包住 SDK 内部多个 HTTP attempt，必要时在 transport 层计数。

### 5.5 Mode B 两阶段状态对账

#### 准备阶段

**[合理推断]**

1. 原子关闭新 run、工具、上传 admission。
2. drain 已受理操作。
3. 确认没有活跃子 agent、UNKNOWN 写工具和不受控后台进程。
4. 冻结外部 Harness 的 graph 状态应用。
5. 模型结果可以进入 Broker journal，但暂不应用到 graph。
6. 选定已持久提交的不可变 checkpoint。
7. 确认对应工具回执已经应用到该 checkpoint。
8. 请求 Actor snapshot，确认目标 UID/generation durable COMPLETED。
9. 独立保留该快照版本并确认成功。

**[合理推断]** before_model 回调不是 checkpoint 已持久提交的证据。若不能可靠获得冻结/提交接缝，DeerFlow 首版只在整个 run 结束且无活跃子 agent 时建立 manifest。

#### 发布阶段

**[合理推断]** 在 AgentCloud 自己的一个 PG 事务中发布：

```text
workspace_id
workspace_generation

session_id
thread_id
checkpoint_ns
checkpoint_id

epoch
barrier_generation

source_actor_uid
template_uid
source_snapshot_uuid
source_generation

tag_uid
tag_snapshot_uuid
tag_generation
fidelity

tool_receipt_set_digest
payload_hash
state = COMMITTED
```

**[合理推断]** receipt 水位必须是已终态、已应用到 checkpoint 的无洞序列或明确集合摘要，不能用并行工具的最大 ID 代替。

#### 故障处理

| 崩溃位置 | 恢复规则 |
|---|---|
| 只有 graph checkpoint | **[合理推断]** 保留 PREPARING，不和任意旧 snapshot 拼接。 |
| Snapshot 完成、PG 发布前 | **[合理推断]** 核验原代次与 receipt 集合后补提交；发生变化则视为孤儿候选。 |
| PG 已提交、ACK 丢失 | **[合理推断]** 相同 operation ID 返回原 manifest。 |
| UNKNOWN 写工具/后台进程 | **[合理推断]** 阻止安全点和 manifest 发布。 |
| UID/template/fidelity 不匹配 | **[合理推断]** 拒绝恢复，除非明确支持应用层重建。 |

#### Tag 的特殊边界

**[已验证事实]**

- Actor 后续快照会替换前代。
- CreateTag 没有 expected generation。
- 它捕获执行当时的 snapshot。
- 最新快照 PENDING 且本地副本丢失时，可能选择旧 durable snapshot。
- Tag 自身 generation 从 1 开始，不等于源 Actor generation。[S13]

**[合理推断]** 因此必须先确认目标源快照 COMPLETED，在生命周期独占期间创建 Tag，再核验来源未变化。manifest 分别保存源和 Tag 的身份，不直接比较 generation 相等。

独立保留必须先于 COMMITTED；Tag 创建未知先查询，不盲目重建或删除已引用对象。

### 5.6 必须保持的不变量

| 编号 | 不变量 |
|---|---|
| I1 | **[合理推断]** 一个 Workspace 同时只有一个可提交写结果的 epoch。 |
| I2 | **[合理推断]** Quiescing 后无新工具；UNKNOWN 写工具阻止安全点。 |
| I3 | **[合理推断]** 只有 COMMITTED 且来源匹配的 manifest 可恢复。 |
| I4 | **[合理推断]** 相同逻辑 ID、不同 payload 必须拒绝。 |
| I5 | **[合理推断]** UNKNOWN 模型/工具副作用不自动重放。 |
| I6 | **[合理推断]** Workspace Suspend 不结束 Trajectory。 |
| I7 | **[合理推断]** 指标/日志只是提示，不能代替 durable 状态。 |
| I8 | **[合理推断]** 未确认的 Suspend 不能被后续 Resume 越过。 |

**[合理推断] 首版限制自动 HA。** 旧控制器的 Suspend 可能在新控制器 Resume 后才到达；公开 API 不验证 AgentCloud epoch，外围锁无法根治。

保底处理是：

- 单写者 actuator。
- 禁止 Actor 名称复用。
- 未决调用进入 RECOVERY_REQUIRED。
- 确认旧执行器及未决调用终止，或取得可靠完成证据后才恢复操作。

**[合理推断]** 若要求自动接管，需要上游在同一 Actor lease 下核验 UID 加版本/激活代次等 precondition。仅 UID 只能防名称复用。

### 5.7 KV 生命周期反馈

```mermaid
sequenceDiagram
    participant C as Coordinator
    participant P as KV Policy Adapter
    participant D as Dynamo
    participant E as Engine

    C->>P: SleepIntent(epoch, seq, expected_gap)
    P->>P: 身份 / 去重 / 成本门槛

    alt 当前只支持请求级 hints
        P-->>C: 静默期不可主动执行，记录观测
        C->>P: 下一次真实模型请求
        P->>D: 已支持的 priority / agent_hints
        D->>E: capability 允许时转发
    else 后续已验证专门 lifecycle 扩展
        P->>D: 版本化 lifecycle event（拟新增）
        D->>E: 已验证的后端操作
        E-->>P: 实际 block / tier 变化证据
        P-->>C: Applied / Unsupported / Unknown
    end

    C->>P: ResumeIntent，新 seq
    P->>P: 取消过期策略，记录重算和回传成本
```

**[合理推断]** P3 按 Observe → Shadow → Enabled 推进。Shadow 预测不能计为收益；没有物理执行证据时，只报告逻辑准入或请求优先级变化。

## 7. Benchmark、消融与分级评测

### 7.1 五主组及归因边界

**[合理推断] 五组不足以完整正交辨识四个开关和交互。** 因此主组报告条件增量，关键交互另补 2×2。

| 组 | S：普通 idle | T：ThunderAgent | Q：等待协调 | K：真实 KV 反馈 | 解释 |
|---|---:|---:|---:|---:|---|
| A | 关 | 关 | 关 | 关 | 标准 KV routing、Actor 常驻。 |
| B | 开 | 关 | 关 | 关 | B−A：普通 idle 的条件收益。 |
| C | 开 | 开 | 关 | 关 | C−B：已有 idle 下 ThunderAgent 的增量。 |
| D | 开 | 开 | 开 | 关 | D−C：本项目等待协调的主要价值。 |
| E | 开 | 开 | 开 | 开 | E−D：真实反馈执行器的增量；无执行器则 N/A。 |

**[合理推断] 公平基线要求：**

- 相同 Gateway/Journal 和持久化级别。
- 相同认证、模型参数、输入轨迹和资源上限。
- 相同基础路由配置。
- 中间件成本计入全部组。
- 另外测直连，仅用于揭示固定代理成本。
- idle 策略至少比较 eager-suspend 与固定 TTL。
- 在独立调参负载上选择简单策略，正式集不重新调赢家。

**[合理推断] Mode A 与 Mode B 分开报告。**

- Mode A 的 D−C 看等待连接外移。
- Mode B 的 D−C 看压力信号是否胜过简单工具闲置策略。

#### 补充实验

**[合理推断]**

- 加 T-only，与 A/B/C 构成 S×T 的 2×2。
- K 可独立于 Q 时，加 C+K，与 C/D/E 构成 Q×K 的 2×2。
- K 依赖 T 时，不能假装存在有效的 `T=0,K=1`。
- 要研究完整交互，另安排因子实验，不把五组阶梯结果称为完全独立贡献。

### 7.3 指标定义

| 指标 | 定义与边界 |
|---|---|
| Actor blocked-residency | **[合理推断]** Actor 驻留且仅因模型等待不能前进的时间积分，单位 Actor·s。 |
| Stranded Worker Time | **[合理推断]** 分别报 reserved core·s、reserved GB·s、实际 working-set GB·s；不能把 Actor 个数当整台 Worker。 |
| Resume p95/p99 | **[合理推断]** 从外部恢复请求进入协调器，到 attach 成功且受控工具可用。另报纯 Substrate RPC。 |
| Stranded KV GB·s | **[合理推断]** 唯一物理块体积乘时间，说明共享、可回收性与是否妨碍活跃工作。 |
| Re-prefill 比例 | **[合理推断]** 上轮已经计算且可复用、这轮被重算的 prefix tokens，占此前可复用 prefix 的比例。 |
| Effective Throughput | **[合理推断]** 每秒正确完成的 turn/任务；另报有效 token/s 与总生成量。 |
| 用户 TTFT | **[合理推断]** 客户端发起逻辑交互到第一条用户可见模型内容，ACK 不算 token。 |
| SLO/Goodput | **[合理推断]** 正确且满足预注册延迟预算的比例/每秒数量；失败、拒绝、超时不能从分母删除。 |
| 单位会话成本 | **[合理推断]** 全系统资源时间与可复现成本模型；资源释放不自动等于云账单下降。 |

#### TTFT 的正确计算

**[合理推断] 串行情况下：**

\[
TTFT_{user}
=
T_{gateway}
+
T_{wake,critical}
+
T_{inference,critical}
+
T_{delivery}.
\]

**[合理推断]** 若唤醒和推理并行，应按实际关键路径计算，不能相加各阶段 p95。Mode B 可能在工具 Actor 未恢复时已经向用户发 token，此时恢复不在该轮 TTFT 上。

#### KV 必须四分类

**[合理推断]**

1. 正在使用或被 pin 的块。
2. 可回收 prefix cache。
3. host/storage tier 的块。
4. 仅存在于调度账本中的逻辑 tokens。

GPU allocator 预分配使 `nvidia-smi` 不一定随 eviction 下降。共享块只按唯一物理块计总量；仍服务活跃 Session 的块不能全部归给休眠者。

**[合理推断]** 没有权威物理 block 数据时，只报告 estimated inactive token·s，不包装成物理 GB·s。

### 7.4 三级环境

| 层级 | 环境 | 能证明什么 |
|---|---|---|
| Level 1 | **[合理推断]** CPU + 真实 Router + Mocker，执行侧可先受控模拟。 | 协议、真实 router 状态、模型内趋势；不能证明真实 GPU 或沙箱性能。 |
| Level 2 | **[合理推断]** 真实 Substrate + 固定 runtime/WorkerPool + 受控推理 backend。 | 网络断连、快照、恢复、执行容量；推理仍可为模拟。 |
| Level 3 | **[合理推断]** 后续有预算与授权时，真实 Dynamo + 固定 vLLM 或 SGLang GPU backend。 | 真实 GPU Goodput、重算与缓存行为。 |

**[合理推断] Mock KV 模型必须冻结：**

\[
B_{gpu}
=
N_{blocks}
\times block\_size
\times bytes\_per\_token.
\]

同时固定：

- rank/TP 容量归属。
- prefix 共享。
- 在用块与可回收块。
- eviction 规则。
- prefill/decode 成本。
- host tier 容量。
- 传输带宽。
- 随机种子。

若使用简化模型，必须显式给出：

\[
L_{prefill}
=
a+bN_{uncached}+cN_{uncached}^2
\]

\[
L_{transfer}
=
B/BW+L_0.
\]

**[合理推断]** 未校准系数只能用于敏感性分析；不能假定一个很高的 prefill 惩罚，再用实验“证明”缓存策略有价值。

### 7.5 统计与故障注入

**[合理推断]**

- 独立重复 run。
- 配对负载种子。
- 按 run/Session 聚类的置信区间。
- 样本不足时不强调 p99。
- 冷缓存与稳态缓存分开。
- 同时报 offered load、成功延迟、失败率和未完成工作。
- 保存原始事件，不只留汇总表。

**[待验证假设] 至少覆盖以下故障窗口：**

- Journal 提交前后。
- 模型发送前后。
- 部分 stream 到达后。
- safe-point ACK 前后。
- snapshot 完成但 manifest 未发布。
- 恢复过程中 Coordinator 崩溃。
- 重复/迟到事件。
- 旧 epoch 写入。
- Actor 同名替换。
- 快照 PENDING/失败。
- MEMORY→ROOTFS 降级。
- 工具超时但仍运行。
- 用户返回与 Suspend 竞态。
- DeerFlow 子 agent/上传并发。

**[合理推断]** 每个窗口要写允许的状态和副作用次数。错配恢复、盲重放 UNKNOWN、把不完整结果标成完成，都应直接阻止进入下一阶段。

## 10. 最终决策与下一步行动

### 10.1 应该做什么

**[合理推断]** 按以下顺序实施：

1. 固定上游。
2. 跑能力探针。
3. 建立安全点与等待代持。
4. 对比强基线。
5. 适配 DeerFlow。
6. 做故障与性能报告。

保留 **Go、真实 Substrate、真实 native Router** 三条工程主线。物理 KV 反馈只在接口和价值都被证实后开展。

### 10.2 绝对不要做什么

**[合理推断]**

- 不重建 AX/kagent 式通用平台。
- 不混用 native 与 Python 原型接口。
- 不把 Workspace Suspend 发成 Dynamo Final。
- 不把逻辑 token accounting 当物理显存。
- 不承诺对象存储跨代增量、任意 TCP 续传和任意模型 exactly-once。
- 不为凑技术栈加入 Rust、Redis、Operator。
- 不在 P0 未通过时开付费资源。
- 不把 Mock 收益写成真实 GPU 简历指标。

### 10.3 P0 第一天先写的验证脚本

**[合理推断]** 后续执行者先写只读契约采集脚本，核心从以下几行开始：

```bash
git -C /tmp/agentcloud-research/substrate rev-parse HEAD
git -C /tmp/agentcloud-research/dynamo rev-parse HEAD

rg -n \
  'message SuspendActorRequest|message ResumeActorRequest|DURABILITY_MODE_' \
  /tmp/agentcloud-research/substrate/api/ateapi/v1/ateapi.proto

rg -n \
  'pause_acting|begin_session_final|force_timed_out' \
  /tmp/agentcloud-research/dynamo/lib/router-plugins/builtin/src/thunderagent/request_classifier/scheduler.rs

rg -n \
  'nvext_agent_context_is_rejected' \
  /tmp/agentcloud-research/dynamo/lib/llm/src/protocols/common/extensions.rs
```

随后只做三个小验证：

1. **连接语义**：Actor 内可控长 HTTP，Suspend 前后记录两端状态。
2. **真实无卡准入**：多 Session 长 prefix 触发 pause，取消等待请求，核验 accounting 和 Final。
3. **最小盈亏曲线**：同容量、同负载、同持久性，比较最佳简单策略与等待协调。

### 10.4 最能一锤定音的实验

**[待验证假设]**

在真实 Substrate 上制造：

> 双拥塞 + 较长模型等待 + 交互请求插入。

固定模型侧负载和执行容量，比较：

- C：普通闲置策略 + ThunderAgent。
- D：C + 等待协调。
- 外置 Harness + 最佳 eager/TTL 强基线。

绘制：

> 等待间隔 / Actor 工作集 → Goodput 差值、blocked-memory GB·s、恢复开销。

同时检查未知与重复副作用。

**[合理推断] 最终决策规则：**

- 如果 D 只赢永远常驻的弱基线，却赢不了外置 Harness 的简单策略，删除“核心跨层调度创新”叙述。
- 如果 C 已达到同等 Goodput，交付恢复协议、适配和负结果。
- 如果 D 在明确资源区间内稳定胜出，且不越过正确性和 SLO 预算，才进入求职正式版。
- B 没有真实物理执行器和归因证据时，不写 GPU KV 释放收益。

**[已验证事实] 当前完成边界：五个上游固定版本的静态审计与计划文档。P0～P6 尚未执行，也没有任何性能提升实测。**
